# Golden drift — 2026-08-19 — `SIM-08-queue-latency`

**Classification: `LAYOUT_FIX_APPROVED`** (a deliberate correction, not an engine upgrade and not
an unexplained regression). One golden affected, one element moved, no data or theme change.

## What changed

`adapters/echarts/option-builder.mjs` → `valueAxis()` now sets `nameLocation: "middle"` and a
`nameGap` whenever a job declares `units`, instead of leaving ECharts' default `nameLocation: "end"`.

| | axis-name (`ms`) transform |
|---|---|
| before | `translate(114 33)` |
| after | `matrix(0,-1,1,0,68,234)` |

## Why it was wrong before

`titleBlock()` places the chart title at `{left: 8, top: 6}`. ECharts' default `nameLocation: "end"`
places a vertical value axis's name at the **top of that axis** — i.e. `(114, 33)`, inside the
title's own text box. Any job declaring both `title` and `units` therefore rendered its unit label
on top of its title. On `bar_horizontal` (a horizontal value axis) the same default pushes the name
past the right edge of the plot area and outside the SVG box entirely.

This was not hypothetical: the committed `SIM-08` baseline above **shipped with the overlap**. It
went unnoticed because only one preset/fixture in the package combines `title` + `units`
(`detector-coverage-heatmap.json`), and it is a heatmap — heatmaps use category axes plus a
`visualMap`, so they never call `valueAxis()`.

Found by measuring rendered text bounding boxes in a browser across a 21-figure document
(`examples/capability-gallery.md`), where three separate chart-engine figures showed the fault:
two title overlaps (`line`, `boxplot`) and one out-of-box axis name (`bar_horizontal`).

The `bubble` builder in the same file already set `nameLocation: "middle"` + `nameGap: 28`
explicitly, so the correct pattern was established in this codebase — `valueAxis()` simply did not
use it.

## Re-baseline

The golden was regenerated by `npm run simulate`. `npm test` passes against the new baseline
(30/30), and the 22/22 acceptance simulations are unchanged.

> **Note on the re-baseline mechanism.** `npm run simulate` rewrites `renders/golden/*`
> unconditionally — the same files `tests/regression.test.mjs` compares against. Running simulate
> after a rendering change therefore re-baselines the goldens silently and erases the drift signal.
> The documented order (`npm test && npm run simulate`) short-circuits on failure and avoids this,
> but nothing enforces it. Always read the `npm test` result *before* running simulate, and record
> the before/after here from that failure output — which is where the "before" transform above came
> from.
