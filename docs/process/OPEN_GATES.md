# Open Gates — every known unfinished thing, written down

**Status:** PROCESS — living register. **This file is the project's memory of what is not done.**

**Why it exists.** An open gate held only in conversation context is deleted by the next session, a
context compaction, or a crash. On a project this size, an unwritten open gate is a permanently open
gate (`LESSONS.md` L-11). Nothing may be "remembered"; everything is written here the moment it is
found. The *raw* findings of each pass, in the verifier's own words and before any judgement, live
in `docs/process/VERIFICATION_LOG.md`; this file holds the curated state.

**What this project IS, and the two purposes it serves at once, is `docs/CHARTER.md`.** Read it
before planning a phase — a register this long is exactly where a build loses sight of its goal.

---

## ⛔ THE PHASE GATE (operator directive, 2026-08-20 — this outranks every disposition below)

> **A phase does not begin while a known defect is open.**
>
> The **only** permitted deferral is a defect whose correction *is the declared main work of a named
> later phase* — predictable by design, already scheduled, and written into that phase's row in
> `docs/plan/BUILD_PLAN.md`. Nothing else may be parked.

This retires four dispositions that had been doing exactly that. `SHOULD_FIX`, `NEXT_SESSION`,
`NICE_TO_HAVE` and open-ended `ACCEPTED` were, in practice, indefinite parking: at the close of
Phase 2 this register carried **26 open rows**, of which 19 sat under one of those four labels with
no date and no owner-forcing event. A register that can absorb an unbounded number of real defects
without ever blocking anything is a to-do list, not a gate.

**Dispositions, complete list:**

| disposition | meaning |
|---|---|
| `BLOCKS_PHASE_N` | A real, open defect. **The next phase may not start until it is closed.** Written with the literal next phase number — `BLOCKS_PHASE_4` while Phase 3 is the last one complete. *(Generalised 2026-08-22: the vocabulary said `BLOCKS_PHASE_3`, which the `register` guard correctly refused the moment a Phase-4 blocker was recorded. The gate was never specific to Phase 3; only its spelling was.)* |
| `SCHEDULED (Phase N)` | Valid **only** if closing it is Phase N's declared main work, and Phase N's `BUILD_PLAN.md` row says so. Anything else here is a `BLOCKS_PHASE_3` in disguise. |
| `NOT_A_DEFECT` | Examined and found not to be a defect: a deliberate design decision, a documented library API, or a pointer to where something really lives. Carries its reasoning, so it is not re-litigated every pass. |

**Rules for this file**
1. Every finding lands here **when found**, not at the end.
2. Every entry carries: id, severity, disposition, evidence, and what *closing* it means.
3. An entry is removed **only** when closed, and closing it is recorded in `CHANGELOG.md`.
4. **The phase gate above decides what blocks.** Severity informs the order of work, never whether
   the work may be skipped.
5. A `NOT_A_DEFECT` row must state *why*, in a form a future verifier can attack. "Accepted" with no
   reasoning is indistinguishable from "ignored".
6. A `SCHEDULED` row must name the phase **and** that phase must name the work. Two documents, one
   claim, checked against each other — the same discipline `CONS-03` applies to the locked-file set.

**`CHANGELOG.md` and `docs/process/VERIFICATION_LOG.md` keep their original numbers, deliberately.**
They are append-only records of what was written at the time, and rewriting a verbatim findings log
to fit a later renumbering is precisely the history-editing this project refuses elsewhere
(`BUILD_PLAN.md` §1 was *dated* rather than rewritten for the same reason). Read them through this
map. Every forward-looking pointer — the plans, the handover, the authoring prompt, the rulebook's
locked-file table — was repaired.

**This cannot recur silently:** `tools/corpus_check/`'s `register` guard refuses a duplicate id in
any tracked table, and its counter-example is retained in `tools/tests/test_corpus_check.py`.
